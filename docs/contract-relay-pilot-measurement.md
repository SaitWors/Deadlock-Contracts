# Протокол измерения Contract Relay

## Дизайн пилота

1. До первого матча зафиксируйте дату начала и конца набора в UTC, срок наблюдения `H` после конца каждого матча, режимы, политику повторных попыток, минимальную практически значимую разницу и версию сайта, Ingest и планировщика. Оставьте одинаковые интервалы опроса провайдера, настройки контрактов и правила Companion в обеих группах. Пример срока наблюдения для регистрации протокола — 24 часа. Срок выбирают до просмотра результатов.
2. Включите согласившихся игроков из закрытого пилота. Предел — 30 участников, ожидаемая активность — 10–15 человек. До первого матча распределите согласившихся участников, которые ещё не являются друзьями Relay, между ранним подключением и отложенным подключением после завершения наблюдения. По возможности распределяйте случайно целые постоянные игровые группы, чтобы сократить смешение данных в общих матчах. Запишите исходное распределение до приглашений. Если случайное распределение невозможно, явно обозначьте результаты как наблюдательное сравнение и сопоставьте группы по режиму, дню, времени игры и настройке Companion.
3. Запишите фактическое состояние дружбы и согласия на момент старта матча. Анализируйте исходное распределение, даже если дружба в ранней группе задержалась. Отдельно покажите анализ по фактическому состоянию. Прекращение согласия прекращает сбор по участнику. Отметьте пропуски и отзыв согласия в сводке по группам.
4. Соберите Match ID независимо от появления в API. Участники отмечают сыгранные с подписанными контрактами матчи по истории официального клиента, в том числе матчи без найденного сервером результата. Сверяйте время конца по провайдеру при появлении данных. При отсутствии серверного времени укажите источник подтверждённого оператором времени и вынесите такие случаи в отдельную проверку чувствительности. Если надёжное время неизвестно, сохраните матч в числе пропусков и исключите его из расчёта длительности.
5. Зафиксируйте определение исхода. Для каждого внешнего Match ID выберите исходную доску с наиболее ранним временем подписи среди подходящих досок группы до старта матча. При равном времени используйте заранее присвоенный локальный ключ доски в лексикографическом порядке. Выбирайте доску по реестру наблюдений до просмотра результата. Считайте первый окончательный автоматический исход выбранного задания этой доски для этого матча. Учитываются `COMPLETED` и `FAILED` с доказательством `VERIFIED_SUMMARY`. Подписание после старта, ручная проверка, предварительная оценка, повторная оценка и завершение задания в более позднем матче не являются исходом этой строки.
6. Матч входит в основное сравнение один раз. Матчи, где в реестре есть участники обеих групп, получат `shared` и будут показаны отдельно. Отдельно укажите долю общих и неопознанных матчей и покажите чувствительность к их исключению. Метаданные публикуются в общем Deadlock API. У контрольной группы может быть доступ к данным, полученным Relay, даже без её участия в запросе.

## Сбор данных

Скопируйте пустой [шаблон CSV](contract-relay-pilot-observations.csv) в закрытое рабочее хранилище пилота. Одна строка соответствует одному внешнему Match ID. Формат времени — ISO 8601 в UTC. Неизвестное поле оставляйте пустым. Match ID связывает игровые данные, поэтому передавайте наружу только агрегаты. Не помещайте в таблицу идентификаторы аккаунтов, журналы, соли реплея, токены или ключи.

| Поля | Источник и значения |
| --- | --- |
| `match_id`, `mode`, `assigned_group` | Внешний Match ID, режим игры, группа исходного распределения `early`, `delayed` или `shared`. Держите отдельно закрытый реестр наблюдений, из которого получена группа. |
| `board_key`, `board_locked_at_utc` | Локальный псевдоним исходной доски и зарегистрированное время её подписи. Связь ключа с внутренним ID храните отдельно. При матче обеих групп поля исходной доски можно оставить пустыми. |
| `consent_at_start`, `friendship_at_start`, `friendship_observed_at_utc` | Сведения, зафиксированные для исходной доски до начала матча. Согласие `yes`, `no`, `unknown`. Дружба `connected`, `disconnected`, `unknown`. Наблюдение дружбы в пределах 24 часов до старта соответствует текущей эвристике админки. |
| `companion_policy`, `companion_signal` | Согласованное состояние Companion `enabled` или `disabled` и наличие принятого терминального сигнала `observed`, `unobserved`, `unknown`. Фиксируйте политику до матча. |
| `started_at_utc`, `ended_at_utc`, `end_source` | Подтверждённые времена матча из `Match` или, если серверные данные отсутствуют, проверенного журнала участника. Источник конца `provider`, `player_record`, `unknown`. |
| `relay_accepted_at_utc`, `relay_ingest_source`, `relay_queue` | Факт приёма записи Ingest из подтверждённого успешного POST по этому Match ID. Источник вроде `gc` берите буквально из записи. Причина выбора очереди `contract`, `friend`, `general`, `unknown` допустима только при явной телеметрии. Сам источник `gc` не определяет очередь. |
| `provider_last_missing_at_utc`, `provider_first_available_at_utc` | Границы наблюдения из существующего опроса по этому же ID и используемому маршруту Deadlock API. Сетевой сбой и 429 не считаются ответом об отсутствии матча. |
| `site_metadata_observed_at_utc`, `auto_final_at_utc` | `Match.relay_provider_metadata_observed_at` и первый подходящий `BoardOption.settled_at` по той же доске и матчу, как в `relay_effectiveness`. Фиксируйте наблюдение, пока сохранены соответствующие сведения об исходе. |
| `follow_up_until_utc`, `outcome` | Последнее время, до которого исход мог быть проверен, максимум конец матча плюс `H`. Используйте `automatic`, `unresolved`, `manual`, `tracking_lost`, `unknown_end`. Ручное решение является отдельным исходом. Эту категорию нельзя смешивать с автоматическим подтверждением. |
| `history_quota_state`, `metadata_quota_state`, `relay_health`, `provider_health` | Для квот `available`, `exhausted`, `limit_signal`, `unknown`, для доступности `available`, `disrupted`, `unknown`. Привязывайте доказательство по времени к окну матча. Лог о rate limit подтверждает сигнал, а точный остаток требует наблюдения счётчиков. |

Существующая админка показывает попытки с привязкой к проверенному матчу и описывает данные, доступные сайту. Используйте её для сверки времени метаданных и исходов. Собственный реестр сыгранных матчей нужен для полного знаменателя. Админское состояние `baseline` в момент привязки не определяет группу эксперимента. В момент сбоя Relay сверяйте heartbeat, состояние Ingest и временные границы источника. При работе с журналом Ingest переносите только поля, перечисленные в таблице. ## Расчёт и вывод

- Дайте по каждой группе число участников, число независимых игровых групп, число подходящих матчей, число общих матчей и причины пропусков. Укажите число автоматических исходов до `H` и долю от матчей с наблюдением до `H` или с более ранним исходом. Покажите долю потерянного наблюдения отдельно. Для проверки чувствительности посчитайте границы доли, считая все потерянные наблюдения сначала без автоматического исхода до `H`, затем с таким исходом.
- Для матчей с полной регистрацией исхода или конца окна используйте ограниченную задержку `min(T, H)`, где `T` — время от конца матча до автоматического исхода. При отсутствии исхода до `H` вклад равен `H`. Сравните средние ограниченные задержки и доли автоматического исхода в обеих группах. Не подставляйте `H` за матч, по которому наблюдение завершилось раньше и исход неизвестен. Вынесите незавершённое наблюдение в отдельный расчёт границ или анализа времени до события с цензурированием.
- Отдельно покажите задержку первого наблюдения метаданных сайтом и время от него до исхода. Для медианы и P90 от конца матча укажите размер выборки и долю без исхода. Если требуемая доля события не достигнута до `H`, укажите, что квантиль за окном. Если публикуете квантиль только по разрешённым матчам, подпишите выборку. Интервалы неопределённости должны учитывать повторные матчи одних и тех же игроков и единицу распределения. При недостатке независимых групп сообщите охват и неопределённость без формальных выводов об эффекте.
- Для утверждения о вкладе Relay требуется подтверждённая последовательность по тому же матчу. Покажите успешный приём Ingest, доступность в API в наблюдаемом интервале и автоматический исход после появления данных. Пересекающиеся интервалы, общий GC-источник без причины выбора, готовые метаданные до Ingest и следы иных источников оставляют происхождение неопределённым. В итоговом отчёте отдельно приведите число матчей с такой последовательностью и эффект распределения по группам с интервалом неопределённости. Итог пилота может оказаться неопределённым либо ограничиться наблюдаемой разницей.
