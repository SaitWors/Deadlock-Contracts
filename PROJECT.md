# Deadlock Contracts — устройство и история проекта

Я начал Deadlock Contracts с простой идеи: дать игроку дополнительные задачи на матч и автоматически проверять их выполнение. Постепенно к этому добавились личный прогресс, Companion, коллекция и инструменты для поддержки проекта. Здесь собрал, как всё устроено, как это запускать и почему некоторые решения менялись.

Описание соответствует исходникам на 11 ноября 2026 года. Версии продукта берутся из `release.json` и `companion/release.json`. Доступность конкретной возможности в production определяется конфигурацией сервера, а не только наличием кода.

Поле `release_date` в корневом manifest осталось от выпуска базовой версии. После этого разработка продолжалась; даты отдельных изменений есть в истории Git. Номер версии сам по себе не доказывает, что сервер уже получил последние коммиты.

Основной сценарий сейчас такой:

1. Игрок входит через Steam.
2. Выбирает режим и от одного до трёх предложенных заданий.
3. Подписывает выбранный набор.
4. Играет матч; Companion показывает предварительный прогресс.
5. Сервер сопоставляет матч с делом и проверяет условия.
6. После подтверждения сохраняются результат и награда.
7. Игрок видит итог, изменение XP и повышение уровня.

Режимы: `STANDARD`, `RANKED` и `STREET_BRAWL`. Количество попыток и срок действия определяет сервер. Интерфейс использует `max_attempts` конкретного дела и не подставляет постоянное число.

Кроме контрактов работают коллекция, ежедневный пак, избранное, витрина, публичные профили, достижения, личная статистика, рейтинг, бюро игроков, совместные операции, объявления и административные инструменты. Некоторые возможности требуют отдельного флага или роли.

Арена, шифр, пользовательский каталог, кошелёк и операции с монетами выведены из действующего пользовательского сценария. Их таблицы, миграции и часть сервисов сохранены для истории, проверки данных и совместимости. Наличие старого компонента или настройки монет не означает, что соответствующий HTTP-маршрут снова открыт.

Отдельной рабочей роли DESIGNER сейчас нет: действующая серверная модель использует OWNER, ADMIN, MODERATOR, TESTER и PLAYER.

## Архитектура и структура репозитория

Это монорепозиторий сайта, сервера и Companion. Основная бизнес-логика находится на backend. Companion и браузер работают с его контрактами данных.

~~~mermaid
flowchart TD
    Web["Сайт React"] --> API["FastAPI"]
    Events["Overwolf GEP"] --> Companion["Companion"]
    Companion --> API
    API --> DB[("PostgreSQL")]
    Worker["Фоновый worker"] <--> DB
    Worker <--> Provider["Deadlock API"]
~~~

В production перед web находится Caddy: он завершает TLS, обслуживает загрузки и проксирует запросы. Redis используется для общего ограничения частоты запросов. Очередь фоновых задач хранится в PostgreSQL; Celery в этом проекте не используется.

## Backend и жизненный цикл контракта

### Генерация и подписание

За доски отвечает `app/services/boards.py`, за генерацию — `contract_factory.py`, `contract_pool.py` и `adaptive_profile.py`.

Для каждого режима создаётся свой набор предложений. Генератор учитывает доступные определения заданий, ограничения режима, сложность и историю. Адаптация использует сохранённые сервером итоговые матчи, раздельно по режимам. Если истории мало, остаётся обычная генерация: отсутствие статистики не должно ломать старт нового игрока.

Условия передаются в структурированном виде: метрика, оператор, целевое значение, режим, сложность и XP. Отображаемый текст не заменяет эти данные.

При подписании сервер проверяет владельца, состояние доски, выбранные option IDs и допустимое число заданий. Выбор и постановка первой фоновой задачи сохраняются в одной транзакции. После блокировки нельзя изменить условия уже начатого дела клиентским запросом.

Время подписания и граница предыдущего матча нужны, чтобы не зачесть старый результат. Reroll работает по серверной политике для ещё не подписанного предложения.

### Попытки и статусы

Статусы задания и статус всего дела — разные вещи. В API нужно сохранять это различие.

| Состояние задания | Что показывать игроку |
| --- | --- |
| `OFFERED` | Можно выбрать предложенное условие |
| `LOCKED` | Выбор зафиксирован, ожидается подходящий матч |
| `VERIFYING` | Идёт получение или проверка итоговых данных |
| `REVIEW_REQUIRED` | Автоматических данных недостаточно или нужен разбор |
| `COMPLETED` | Условие подтверждено |
| `FAILED` | Условие не выполнено по подтверждённому результату |
| `EXPIRED` | Срок действия завершён |
| `VOID` | Задание отменено по серверной политике |

Ожидание провайдера, незавершённая проверка и реальный проигрыш задания не должны выглядеть одинаково. Последняя попытка в VERIFYING или REVIEW_REQUIRED ещё не разрешает показывать окончательный провал.

История выдаётся целыми делами: выбранные задания одного контракта не разрезаются между страницами. Для объяснения результата сохраняются связь с матчем, последняя попытка и последняя оценка, даже если временная привязка уже освобождена для повторной попытки.

### Фоновые задачи

`app/services/jobs.py` хранит задания в PostgreSQL. У задачи есть тип, payload, срок следующего запуска, число попыток, статус и владелец аренды.

Worker выбирает доступную задачу через `FOR UPDATE SKIP LOCKED`. Аренда продлевается отдельно, а завершение проверяет владельца и номер попытки. Это защищает от ситуации, когда старый обработчик после потери аренды записывает результат поверх нового.

Зависшие RUNNING возвращаются в очередь не только на старте worker, но и при обычном опросе. Иначе быстрый перезапуск до истечения аренды мог оставить задачу без дальнейшей обработки.

Идемпотентность работает на нескольких уровнях:

- ключ постановки задачи;
- отсутствие второго активного evaluator для той же пары «дело + матч»;
- привязка входящего события к устройству и игровой сессии;
- уникальные записи награды;
- повторная выдача уже сохранённой квитанции вместо новой операции.

Для внешних уведомлений используется outbox с повторными попытками и диагностикой ошибок. Сетевой сбой не должен откатывать уже сохранённый результат игрока.

### XP, уровни и завершение дела

Награды сохраняются в `RewardLedgerEntry`. Результат задания и запись о начислении согласуются на сервере. Административная корректировка XP имеет отдельное происхождение и не выдаётся за награду конкретного контракта.

Цена перехода с уровня L:

~~~text
100 + 25 × L + 5 × L²
~~~

Новый профиль начинается с первого уровня. Для переходов нужны 130, 170, 220, 280 XP и далее по формуле. Реализация находится в `app/services/progression.py`.

С ноября 2026 года у завершённого дела есть сохранённый `completion_result`. Он фиксируется в транзакции выдачи награды. В него входят реальные выбранные задания, их результат, XP и диапазон уровней. Повтор анимации читает этот снимок и не зависит от того, сколько опыта игрок получил позже.

Для старых дел сервер восстанавливает сцену только при доказуемой цепочке ledger. Если исходное состояние нельзя подтвердить, интерфейс показывает сохранённый итог без выдуманной стартовой шкалы.

<a id="match-verification"></a>
## Проверка матчей и модель доверия

Самая трудная часть проекта — не сравнение числа убийств с условием, а установление того, какой матч относится к делу и какие данные уже окончательные.

### Два пути проверки

| Путь | Что делает сервер | Условия использования |
| --- | --- | --- |
| Provider-based | Находит подходящий матч, получает итоговые данные Deadlock API, нормализует и оценивает условия | Обычный путь; зависит от доступности данных провайдера |
| Companion-first GEP settlement | Проверяет попытку, устройство, сессию, exact Match ID и допустимые финальные факты Companion | Только при включённых флагах и разрешённом аккаунте |
| Асинхронный аудит GEP-результата | Позже сопоставляет результат с независимыми данными провайдера | Отдельный флаг аудита; не превращает клиентский progress в награду |

Основные модули: `providers.py`, `normalization.py`, `evaluator.py`, `match_trust.py`, `gep_settlement.py`, `match_audit.py` и `app/worker.py`.

В обычном provider-пути свежий независимый результат заменяет предварительные клиентские факты. В Companion-first пути аудит работает отдельно от первичного settlement. Эти режимы нельзя описывать как одну безусловную политику «кто прислал данные последним, тот прав».

### Что проверяется

- Авторизованное устройство и его владелец.
- Игровая сессия и причинная связь start → final.
- Точный Match ID и отсутствие подмены матчем соседней сессии.
- Режим, участник, время, состояние попытки и соответствие подписанному делу.
- Терминальное доказательство и допустимые поля финального пакета.
- Повторные запросы, уже обработанные события и конфликтующие данные.
- Возможность достоверно вычислить каждое условие.

Клиент не отправляет готовое решение «контракт выполнен» и не задаёт величину награды. Предварительный прогресс может меняться; подтверждённый серверный результат имеет отдельный статус.

Если обязательных данных нет, сервер повторяет проверку или создаёт внутреннюю заявку. UNKNOWN не должен незаметно превращаться в ноль. Например, неизвестный исход матча нельзя трактовать как поражение, а отсутствующую длительность — как матч длиной 0 секунд.

| --- | --- |
| `MATCH_PROVIDER` | Источник матчей; локально по умолчанию mock |

В исходниках rollout GEP и рекламы по умолчанию ограничен. Перед включением проверяются фактический `/api/status`, конфигурация сервера и реальный матч. Само наличие кода не считается завершённым canary.

### Авторизация и безопасность

Для сайта используется Steam OpenID, серверная сессия и cookie с HttpOnly, Secure и SameSite. Изменяющие запросы проверяют CSRF. Пользовательские операции дополнительно проверяют владельца объекта.

Pairing-код одноразовый и ограничен временем жизни. Устройство можно отозвать; отозванное устройство не должно продолжать выдавать себя за активное. Токены не попадают в логи, публичные снимки, QA-комплекты и web-localStorage.

Права определяет `app/services/permissions.py`:

| Роль | Область доступа |
| --- | --- |
| OWNER | Все предусмотренные разрешения; определяется защищённой серверной политикой |
| ADMIN | Административное чтение, проверка, часть управления контентом и диагностика |
| MODERATOR | Очередь проверки и модерация бюро |
| TESTER | Пользовательский доступ с отметкой тестера, без административных прав |
| PLAYER | Обычный пользователь |

Конкретное действие проверяет permission, а не только надпись роли. Для чувствительных административных операций предусмотрено TOTP-повышение доступа. Вход через reviewer gateway не выдаёт права администратора.

В production применяются trusted hosts, ограниченное доверие reverse proxy, CSP и другие защитные заголовки, общий rate limiter, лимиты body и evidence. Web и worker запускаются без root, с read-only корнем, ограничениями ресурсов и сброшенными capabilities. PostgreSQL и Redis не публикуются наружу.

### Очередь проверки

Внутренний review создаётся системой при недостатке или конфликте данных. Модератор получает claim с ограниченным сроком, изучает факты и принимает решение через серверный moderation service. Повтор решения и конкурирующие действия проверяются транзакционно.

Обновление провайдера не должно обходить активный claim. Все изменения оставляют audit-запись. Старые endpoints ручной отправки произвольных доказательств отключены.

### Telegram и объявления

Telegram-интеграция включает исходящие уведомления модерации, одноразовую привязку модератора, защищённый webhook, callback-claim и черновики решений. Финальное начисление наград из чата не объявляется реализованным.

Токен бота и секрет webhook хранятся в secrets. Входящий запрос проверяет секрет; callback связан с серверной привязкой и текущим состоянием review.

Системные объявления имеют аудиторию, срок, локализацию и отдельные поверхности сайта и Companion. Для выкладки есть флаги и тестовые аудитории. Зеркалирование в Telegram включается отдельно.

Публичный контакт поддержки — [@deadlockts_bot](https://t.me/deadlockts_bot). В `/api/status` контакт публикуется через `contact_url`.

### Сообщество и приватность

Профили, бюро игроков, совместные операции и достижения опираются на серверные сервисы `community.py`, `bureaus.py`, `bureau_operations.py`, `achievements.py` и `personal_progress.py`.

Публичный рейтинг учитывает настройки видимости профиля и статистики. Закрытый профиль не должен попадать в публичную выдачу через соседний endpoint. Личная статистика отличает подтверждённые данные от предварительных; административные прибавки XP не подменяют историю выполненных контрактов.

### Оформление

Я несколько раз менял визуальный подход. Текущий вариант — цифровое бюро на фоне города Deadlock: тёмные панели, компактная навигация, выразительная пентаграмма, один заметный контракт на первом экране. Пергамент, свитки и декорации старых версий больше не определяют рабочий интерфейс.

Семантические цвета принадлежат `frontend/src/appearance.css`. Исторические имена вроде `--ns-paper` остаются совместимыми алиасами, а не требованием рисовать бежевый лист.

| Назначение | Тёмная тема |
| --- | --- |
| Фон / глубокий фон | #0b0d0d / #090b0b |
| Поверхность / приподнятая поверхность | #13191c / #1d2529 |
| Граница | #303b40 |
| Основной / вторичный текст | #edf1ef / #a5b0b4 |
| Акцент и заливка | #aec69b |
| Текст на акценте | #172017 |
| Предупреждение / ошибка / информация | #cfbc8e / #e6a8a0 / #9eb9bb |

Есть dark, light, black, custom и system. Custom сохраняет выбранную заливку и подбирает читаемый текст/акцент. System следует предпочтениям ОС. Цвета статуса не заменяют текстовое объяснение.

Основной интерфейс использует локальные Inter и Valve Oracle с fallback. Отдельные публичные документы сохраняют локальный Jost. Кириллица и английские строки проверяются отдельно. Стили standalone-страниц находятся в `app/static/nightshift-documents.css`.

Типовые панели почти прямоугольные: базовое скругление 4 px, панели 2 px. Контейнер публичной части — до 79 rem; отступы уменьшаются на узких экранах. Контракт должен оставаться читаемым на 320 px.

Иконки основной навигации — Hugeicons Free Stroke Rounded через официальные пакеты. В остальном интерфейсе сохранены локальные Lucide SVG. Иконка не должна быть единственным объяснением статуса или действия.

### Выбор и подписание

Карточка показывает категорию, условие и XP отдельно. Наведение, нажатие и выбранное состояние заметны, но не закрывают условие. Выбор ограничен серверными правилами.

Подпись — визуальная настройка. Текст и рисунок могут сохраняться в localStorage этого браузера отдельно для аккаунта; это не электронная подпись и не способ аутентификации. Ошибка хранения не мешает подписать дело. Для рисунка сохраняются ограниченные нормализованные координаты, а не произвольный SVG.

Успех появляется после серверного подтверждения. Повторное нажатие, закрытие анимации или пропуск не создают второе подписание. Ошибка оставляет возможность восстановиться без потери контекста.

### Коллекция и ежедневный пак

Игрок получает один бесплатный пак на календарный день UTC. Сброс — в 00:00 UTC, то есть в 03:00 МСК.

Состав и квитанция сохраняются до анимации открытия. При потере ответа интерфейс восстанавливает ту же операцию. Повтор старого ключа после полуночи возвращает его исходную квитанцию; новый день не должен превращать retry во вторую выдачу старого запроса.

Пустой или неполный пул не расходует дневную возможность. Избранное и витрина остаются доступны. Административные черновики карточек, проверка и настройка паков отделены от пользовательских закрытых операций экономики.

Открытие использует стопку, последовательный переворот и эффекты редкости. Доступны пропуск, клавиатура и уменьшенное движение. Быстрая или повторная анимация не меняет инвентарь.

### Сцена завершения

В готовой сцене остаются одна плашка профиля с уровнем и от одной до трёх плашек реальных заданий. Плашки появляются сверху и продолжают плавно двигаться.

Невыполненные задания сереют, раскалываются и исчезают первыми. Выполненные по очереди летят к шкале; число и заполнение меняются по одной временной последовательности. При достижении порога та же плашка профиля смещается к центру, увеличивается и показывает новый уровень. Остаток XP заполняет следующую шкалу.

При нескольких повышениях каждый серверный порог обрабатывается последовательно. Задержанные кадры не должны потерять XP или пропустить уровень. Повтор читает сохранённый результат дела.

Esc закрывает сцену и восстанавливает фокус. На телефоне профиль находится над заданиями. Reduced motion показывает короткий итог вместо длинной сцены.

Сохранённые материалы: [вход и парение](docs/design/cinematic-finale/01-floating.png), [раскол задания](docs/design/cinematic-finale/02-shatter.png), [повышение уровня](docs/design/cinematic-finale/03-levelup.png), [запись сцены](docs/design/cinematic-finale/finale.mp4).

### Общие правила интерфейса

- У ожидания, пустого состояния, ошибки и успеха есть самостоятельное представление.
- Фоновое обновление не уничтожает открытую сцену и не сбрасывает действие пользователя.
- Диалоги поддерживают клавиатуру, закрытие и возврат фокуса.
- Сохранённое и системное уменьшение движения учитываются во всех значимых эффектах.
- Декоративный фон не мешает читать условия; видео останавливается в скрытой вкладке.
- RU/EN, длинные названия, мобильное меню и отсутствие горизонтального переполнения проверяются вместе с изменениями.
- Общие стили меняются у их владельца; новые слои переопределений добавляются только при необходимости.
- Размер JS, CSS и ассетов ограничен существующими бюджетами из `scripts/check_frontend_budget.py`.

### Сессия и конец матча

Каждый матч получает неизменяемую локальную Session ID. Match ID может появиться позже. Поздний идентификатор дополняет ту же сессию, а не создаёт новую причинную цепочку.

Закрытие игры, меню и неопределённая фаза не считаются достаточным доказательством конца матча. После терминального сигнала открывается ограниченное окно сбора поздних данных — пять секунд. Финальный снимок фиксируется при commit, сохраняется в durable queue, и только затем жизненный цикл считается завершённым.

Состояние terminal pending, доказательство и deadline восстанавливаются после перезапуска. Явный Exit должен сохранить ожидающий финал. После reconnect повтор использует прежний ключ идемпотентности.

Final не обходит не подтверждённый сервером start той же сессии. Очередь хранит причинный ключ даже при переходе от неизвестного Match ID к точному. Зависший IN_FLIGHT после рестарта восстанавливается в повторную доставку.

Новая игра очищает матчевые метрики. Старый cached Match ID предыдущего финала не привязывается к следующей сессии. Outcome, пришедший до Match ID, сначала относится к Session ID.

Для Street Brawl PostGame между раундами не завершает всю scoring-session. Частичный roster не стирает ранее накопленные значения, а временно меньший clock не откатывает progress.

Данные, пришедшие произвольно поздно после grace window, не объявлены полностью решённой задачей. Для их обработки нужен отдельный серверный контракт пересмотра, а не незаметное изменение уже замороженного пакета.

### Предварительный прогресс

Overlay и Desktop показывают оценку по доступным live-фактам. Для `lte` и `eq` есть отдельные состояния: «пока в пределах лимита» не равно окончательному выполнению.

Неизвестное поле остаётся неизвестным. Локальная арифметика не заменяет серверный verdict. Окончательная сумма XP читается из подтверждённого ответа.

### Реклама

Рекламный слот имеет отдельную возможность `desktop_ads_v1` и серверное управление. Он закрыт для overlay, gameplay, FTUE, pairing, диалогов, ошибок и пустых состояний. Во время жизни процесса Deadlock Desktop-реклама также скрывается.

Реклама остаётся выключенной до отдельной проверки на конкретном OPK. Disabled и no-fill не доказывают успешную показанную рекламу.

## База данных и миграции

PostgreSQL хранит пользователей, сессии, устройства, определения заданий, доски и выбранные условия, матчи, попытки и evidence, очередь, outbox, review, ledger, объявления, бюро и коллекцию.

Основные связи:

- пользователь владеет досками, устройствами, профилем и инвентарём;
- доска относится к режиму и содержит предложенные задания;
- выбранные задания проверяются по попыткам и конкретным матчам;
- награда связана с источником и заданием;
- review связан с проверяемым объектом, claim и аудитом;
- операция пака связана с сохранённой квитанцией и полученными карточками.

Уникальные ограничения и транзакции дополняют прикладную идемпотентность. Для конкурентных операций на PostgreSQL используются блокировки строк. SQLite в части тестов не заменяет проверку поведения PostgreSQL.

<a id="development"></a>
## Локальная разработка

### Запуск через Docker

~~~bash
git clone https://github.com/SaitWors/Deadlock-Contracts.git
cd Deadlock-Contracts
docker compose up -d --build
docker compose ps
~~~

Основной адрес — http://localhost:8080/ru/. Тестовая сессия — http://localhost:8080/dev/preview.

Локальная конфигурация запускает PostgreSQL, web и worker. Web сначала применяет миграции, worker ждёт его готовности. Данные PostgreSQL и evidence находятся в отдельных volumes.

Провайдер по умолчанию — mock. Demo auth и dev endpoints разрешены только в development. Их нельзя переносить в production.

### Backend без контейнера

Нужны Python 3.13, PostgreSQL и переменные среды для development:

~~~bash
python -m venv .venv
~~~

После создания окружения нужно активировать его: `source .venv/bin/activate` в Linux или `.\.venv\Scripts\Activate.ps1` в PowerShell. Установку зависимостей выполнять из активированного окружения.

~~~bash
python -m pip install -r requirements-dev.txt
~~~

Задать `DATABASE_URL`, `SESSION_SECRET`, `APP_ENV=development`, допустимый `APP_BASE_URL` и `TRUSTED_HOSTS`. Для изолированной разработки использовать `MATCH_PROVIDER=mock`. Значения для production здесь не копируются.

~~~bash
python -m app.migrate
python -m uvicorn app.main:app --host 127.0.0.1 --port 8080 --reload
~~~

Worker запускается отдельно из того же окружения:

~~~bash
python -m app.worker
~~~

### Frontend отдельно

Нужны Node.js 22 и версия pnpm из `frontend/package.json`:

~~~bash
cd frontend
corepack enable
pnpm install --frozen-lockfile
pnpm dev
~~~

Настройки Vite и proxy находятся в `frontend/vite.config.ts`. Backend должен работать отдельно; frontend dev server сам не создаёт таблицы и не запускает worker.

Для удалённой среды можно использовать `scripts/preview-codespace.sh`. Это отдельная development-конфигурация, а не production-деплой.

### Просмотр Companion

Без Overwolf доступен только интерфейсный/fixture-сценарий; браузер не воспроизводит реальные API игры. Полноценная установка выполняется через Developer Options или разрешённый тестовый канал Overwolf после сборки OPK.

<a id="production"></a>
## Production и обновление

### Состав

Production Compose запускает Caddy, PostgreSQL, Redis, одноразовый migrate, web и worker. Название Compose-проекта — `deadlock-contracts`.

Сети разделены на edge, внутреннюю data и outbound. Web и worker используют одну схему данных, но выполняют разные процессы. Внешние порты открываются у Caddy; база и Redis остаются внутри Docker.

Dockerfile сначала собирает Vite frontend, затем помещает его в Python runtime. Поэтому изменение исходников React без пересборки образа не меняет опубликованный сайт.

### Первичная настройка

Нужны Linux-сервер, Docker Compose, домен с настроенным DNS, доступные 80/443 и место под базу, evidence и резервные копии.

~~~bash
cp .env.production.example .env.production
chmod 600 .env.production
./scripts/init-secrets.sh
./scripts/set-api-key.sh steam
./scripts/set-api-key.sh deadlock
./scripts/init-admin-totp.sh
~~~

В `.env.production` задаются DOMAIN, ACME_EMAIL, режим альфы, разрешённые Steam ID, ссылка на Companion и необходимые флаги. Секреты находятся в `secrets/*.txt` и монтируются read-only.

Если нужен reviewer gateway, отдельно используется `scripts/init-qa-access.sh`. Его код хранится как SHA-256 и имеет срок действия. Истёкшая дата из примера конфигурации не становится рабочей только от копирования файла.

Настройки Telegram и объявлений включаются по мере готовности соответствующей интеграции. Для обычного запуска они не обязательны.

Перед первым запуском:

~~~bash
python3 scripts/release_check.py .
./scripts/preflight.sh
docker compose --env-file .env.production -f compose.prod.yaml config --quiet
docker compose --env-file .env.production -f compose.prod.yaml up -d --build
~~~

`.env.production`, secrets, backups и runtime не должны попадать в Git или исходный ZIP. Для приватного ключа, токена и дампа нет безопасной причины добавлять их в документацию.

### Обновление существующей установки

Из checkout нужной ревизии с сохранёнными production-настройками:

~~~bash
./scripts/preflight.sh
./scripts/deploy-current.sh
~~~

Штатный сценарий сверяет версии, проверяет исходники, собирает образы, запускает зависимости, делает проверенную резервную копию перед миграцией, применяет миграции и обновляет процессы. После запуска проверяет web, Redis, worker и опубликованный Caddy.

Для контроля:

~~~bash
docker compose --env-file .env.production -f compose.prod.yaml ps
docker compose --env-file .env.production -f compose.prod.yaml logs --since=10m web worker redis
curl -fsS https://deadlock-contracts.online/api/health
curl -fsS https://deadlock-contracts.online/api/ready
curl -fsS https://deadlock-contracts.online/api/status
~~~

Health показывает живой процесс, ready — готовность зависимостей, status — версию и публичные возможности. Эти проверки не заменяют вход, подписание и настоящий матч.

При работе с отдельными каталогами релизов нужно сохранить тот же Compose-проект, нужные volumes, `.env.production` и secrets. Нельзя случайно получить вторую пустую базу из-за другого имени проекта.

<a id="restore"></a>
## Резервное копирование и восстановление

Создание копии:

~~~bash
./scripts/backup.sh
~~~

Скрипт сохраняет SQL gzip и SHA-256 sidecar. Копия базы не включает secrets, конфигурацию, evidence volume, загрузки Companion и состояние Caddy; они сохраняются отдельно.

Восстановление:

~~~bash
./scripts/restore.sh backups/selected-backup.sql.gz
~~~

Сценарий проверяет приватную копию архива, gzip и доступную контрольную сумму, создаёт уникальную пробную базу, импортирует данные ограниченной ролью и проверяет совместимость со схемой выбранных образов приложения. Проверка выполняется до остановки web и worker.

При переключении исходная рабочая база не удаляется. Она сохраняется под уникальным именем `deadlock_contracts_previous_<timestamp>_<random>` с запрещёнными подключениями. Идентичность баз отслеживается по OID, включая потерю ответа после COMMIT.

После успешного переключения и после ошибки на этапе cutover web и worker остаются остановлены. Сначала нужно выбрать и проверить совместимые образы, затем явно возобновить процессы. Автоматический старт с неподходящей схемой опаснее заметной остановки.

Если автоматический откат не подтверждён, нужно сохранить обе базы и их OID, проверить текущее имя live/previous/trial, определить завершённость переименования и согласовать схему с выбранным приложением. Повторять restore вслепую или удалять предыдущую базу нельзя.

Требования сценария: Bash, Docker Compose, gzip, Python 3, flock и подходящий psql; текущий Compose использует PostgreSQL 17.6. Проверяется формат SQL, отклоняются запрещённые команды переключения и выполнение psql-команд. Контрольная сумма обнаруживает повреждение, но сама по себе не доказывает доверенное происхождение копии.

Для проверки восстановления нужна отдельная одноразовая среда: исходные данные → backup → пробный restore → сравнение данных и сохранённой предыдущей базы → ошибка переименования → проверка отката. Unit-тесты сценария не заменяют работу настоящего PostgreSQL и Docker.

### Companion

~~~bash
cd companion
npm run release:check
npm run test:qa-bundle
npm run build:opk
npm run verify:opk
npm run build:qa-bundle
~~~

Для упаковки нужны Node.js и стандартные Linux-утилиты zip, unzip и sha256sum. Windows runtime приложения и Linux builder — разные среды.

OPK содержит runtime-файлы, SBOM перечисляет их хеши. Воспроизводимость проверяется повторной сборкой из распакованного source ZIP и сравнением SHA-256.

QA-комплект содержит:

| Файл или каталог | Назначение |
| --- | --- |
| `PROJECT.md` | Общая инструкция, описание совместимости и ручная матрица |
| `CANDIDATE.json` | Идентичность конкретного кандидата и его артефактов |
| `OPK/` | OPK, SBOM и контрольные суммы |
| `SOURCE/` | Исходники для повторной сборки |
| `BUNDLE_CONTENT_SHA256SUMS.txt` | Контрольные суммы содержимого комплекта |

При упаковке самостоятельного Companion общая документация копируется внутрь его исходного архива. В монорепозитории она хранится один раз, в корне.

`CANDIDATE.json` фиксирует версии, хеши и автоматические проверки упаковки. Поля manual_qa, overwolf_submission и overwolf_approval не получают положительный результат автоматически.

### CI и границы проверки

Workflow содержит пять основных направлений: backend, frontend, миграции PostgreSQL, Companion/OPK и Docker release image.

Исторические результаты относятся к конкретным ревизиям. Например, в PR №62 записаны 944 пройденных backend-теста и один skip; в PR №60 — 307 frontend-тестов. Это история проверок тех изменений, а не свежий результат для любого следующего коммита.

Мок-провайдер, JSDOM, fixture-запись анимации и автоматическая сборка OPK полезны, но не подтверждают настоящий Steam-вход, матч Deadlock, фокус Overwolf и одобрение QA.

<a id="seo"></a>
## SEO и публичные страницы

Публичные страницы должны отдавать осмысленный HTML без обязательного запуска React. Контент RU/EN разделяется по адресам и использует согласованные canonical/hreflang, title, description, Open Graph и структурированные данные.

Канонический публичный контент хранится в `shared/public-pages.json`. Серверная генерация находится в `app/seo.py`, frontend-маршруты — в `frontend/src/publicRoutes.ts`.

Есть robots.txt, sitemap.xml, social preview и совместимость старых адресов. Неизвестный адрес должен возвращать настоящий 404, а не копию главной с кодом 200. Приватные и development-страницы не должны становиться индексируемыми посадочными страницами.

После выкладки:

~~~bash
curl -I https://deadlock-contracts.online/en/cards
curl -I https://deadlock-contracts.online/not-a-real-page
curl -I https://deadlock-contracts.online/social-preview.jpg
curl -fsS https://deadlock-contracts.online/robots.txt
curl -fsS https://deadlock-contracts.online/sitemap.xml
python3 scripts/audit_discovery.py
python3 scripts/audit_discovery.py --user-agent OAI-SearchBot
~~~

Google Search Console и Bing Webmaster Tools требуют отдельного подтверждения домена и отправки sitemap. Само изменение README или meta-тегов не гарантирует индексацию и позицию в поиске.

IndexNow включается публичным ключом `INDEXNOW_KEY`. Сначала используется dry run:

~~~bash
python3 scripts/submit_indexnow.py --base-url https://deadlock-contracts.online
~~~

Отправка выполняется отдельно с `--submit` после проверки опубликованного ключа и адресов. Ключ IndexNow не является Steam API key или секретом сессии.

Содержимое публичных описаний должно совпадать с текущим продуктом: контракты, прогресс, Companion и коллекция. Закрытые эксперименты не рекламируются как действующие возможности.

<a id="troubleshooting"></a>
## Частые проблемы

| Симптом | Что проверять |
| --- | --- |
| После обновления старый дизайн | Нужный commit в checkout, пересборку web, образ контейнера, каталог Compose и Caddy, ответ опубликованного HTML |
| Версия та же, код разный | Сравнивать commit и собранный артефакт; номер базового alpha-выпуска менялся не при каждом PR |
| Вход Steam не завершается | APP_BASE_URL, домен, HTTPS, cookie, trusted hosts, OpenID callback и часы |
| Контракт долго VERIFYING | Доступность провайдера, Match ID, worker, очередь, retry и внутренний review |
| Матч не найден | Время подписания, режим, аккаунт, поздний Match ID, историю провайдера и GEP |
| Companion offline | Pairing/revoke, версию, токен, доступность backend, bootstrap и heartbeat |
| Overlay показывает другое условие | Выбранный режим, активное дело и поддержанные live-метрики; final берётся только с сервера |
| После рестарта ждёт финал | Состояние durable queue, predecessor ACK, terminal pending и последнюю сетевую ошибку |
| Ежедневный пак уже получен | Дату UTC, сохранённую квитанцию и исходный ключ запроса |
| Ошибка на повторе пака | Сначала восстановить прежнюю операцию, не создавать бесконечно новые ключи |
| Нет кнопок админки | Серверную роль, permissions и TOTP, а не только badge |
| Telegram callback отклонён | Привязку модератора, webhook secret, срок claim и текущую версию review |
| Ready не проходит | PostgreSQL, Redis, миграции и доступность необходимых зависимостей |
| Worker перезапускается | Логи, traceback, конфигурацию, схему и число рестартов |
| OPK не совпадает с версией | release.json, manifest, release-meta и SHA-256 именно упакованного файла |
| Поисковик не видит страницы | Код ответа, HTML без JS, robots, sitemap, canonical и подтверждение домена |

У повторной проверки должен быть понятный объект: дело, задача, устройство или артефакт. Исправление «перезапустить всё и выдать XP ещё раз» нарушает модель данных.

<a id="history"></a>
## История разработки

### Как менялся проект

**Август 2026: проверка матчей и основа Companion.** Сначала я собирал работоспособный цикл «выбор → матч → проверка → XP». Основное время ушло на доверие к evidence, нормализацию ответов, задержку итогов провайдера, правильную привязку и восстановление после сбоев. Затем появился отдельный Companion-first путь с попыткой, lease и асинхронным аудитом.

**Сентябрь 2026: поддержка проекта и прогресс игрока.** Добавил роли, отдельный moderation service, claim review, Telegram-привязку и объявления. После этого расширял личный кабинет: достижения, бюро, совместные операции, карточки, пакеты, профиль и мобильную навигацию. Параллельно переделывал первое знакомство с сайтом и публичные страницы.

**Конец сентября и октябрь: несколько итераций дизайна.** Были Nightshift и оформление по City Never Sleeps. Я переносил общий стиль на кабинет, админку, подписание и Companion, добавлял новые карточки и голосование. Отдельно исправлял settlement, восстановление, историю и источники личной статистики.

**Октябрь: эксперимент с экономикой и ареной.** Появились монеты, карточная экономика, EX-стороны и бой в стиле Гвинта. При этом пришлось восстанавливать прежнюю коллекцию и следить, чтобы смена каталога не ломала инвентарь. Позже я решил сократить основной пользовательский сценарий и убрать арену, шифр и монеты из действующего интерфейса.

**Ноябрь: контракты снова в центре.** Переработал главную и доску, упростил навигацию, сделал бесплатный ежедневный пак. Подписание прошло через вариант со свитком и пергаментом, затем рабочие поверхности стали цифровыми. Добавил сохраняемую подпись, общий фон, навигационные иконки, сцену завершения и неизменяемый снимок результата. Последним изменением контакты поддержки перевёл на Telegram-бота.

Из этой истории для меня главный вывод: лучше довести один понятный цикл до надёжной работы, чем постоянно расширять интерфейс новыми системами. Поэтому в текущем варианте сначала идут контракты, результат и личный прогресс.

## Дальнейшая работа

Я хочу сначала укрепить основной сценарий: вход → выбор → матч → понятный итог.

Ближайшие технические задачи:

1. Проверить ограниченный GEP rollout на настоящих матчах и зафиксированном OPK, прежде чем расширять аудиторию.
2. Уменьшить накопившийся CSS и разделить крупные frontend-модули, сохранив существующее поведение.
3. Сократить неоднозначность ожидания: объяснять игроку, что именно проверяется и когда нужен review.
4. Проверить восстановление на отдельном настоящем PostgreSQL/Docker-стенде.
5. Поддерживать актуальную Windows/Overwolf QA-матрицу и связь результатов с хешем кандидата.
6. Улучшать публичное описание и индексацию по фактическому содержанию сайта.

Роль дизайнера и её отдельная студия требуют новой серверной модели прав и законченного процесса публикации. Это направление, а не готовая возможность.

Возвращать арену или монетную экономику только ради количества функций не планирую. Их старый код важен для сохранности данных, но не должен отвлекать от основного продукта.
