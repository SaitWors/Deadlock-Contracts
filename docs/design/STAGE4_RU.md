# Этап 4 — мастерская карточек и архив без Companion

Дата: 8 сентября 2026. Основа: main после PR №33 (`e40df047`).

## Что получает игрок

В меню аккаунта: аватар, имя, уровень, XP, реальный баланс жетонов архива, переход к заработку, профиль, своё место в рейтинге, достижения, бюро, мастерская, заявки и история жетонов. Выход закрывает сессию. Меню адаптировано по присланному скриншоту ReManga: собственная палитра, латунь и бумажный архив, без неработающих кнопок оплаты и подписки.

На главной кабинета — вход в браузерные занятия. Раздел «Архив карточек» работает после обычного Steam-входа, без установки Companion и доступа к Overwolf разработчика. История настоящих контрактов доступна отдельно через меню.

## Создатель карточек

Любой активный пользователь может выбрать героя, ранг, название варианта, изображение, масштаб и положение; добавить описание, авторство и источник; сохранить черновик и отправить заявку. Дизайн можно посмотреть до отправки. До публикации он виден автору и, после отправки, сотруднику с правом проверки.

Ранги: **F, E, D, C, B, A, S, SS, SSS**. Девять переиспользуемых оформлений поверх изображения используют общий SVG-компонент с разной геометрией, детализацией и цветом. Одна иллюстрация не требует девяти отдельных файлов с нарисованной рамкой. Версия оформления хранится вместе с дизайном (`frame_version=1`); дальнейшие версии должны сохранять отображение уже опубликованных дизайнов.

Список 38 героев взят как снимок [Deadlock API: Heroes](https://deadlock-api.com/heroes) от 8 сентября 2026. Ключи каталога — собственные строковые идентификаторы, не Valve hero ID. Сайт не запрашивает внешний сервис при каждом открытии редактора. Список можно дополнить отдельным изменением `app/services/archive.py`.

**Количество:** девять базовых рангов × 38 героев = 342 карточки. Для примерно 370 можно добавить 28 вариантов. Диапазон 8–10 на героя — план наполнения, не ограничение базы. Один герой может иметь несколько дизайнов одного ранга. Никакие 342 пустые карточки автоматически не публикуются.

Каталог содержит только опубликованные дизайны: поиск по названию/автору, фильтры по герою и рангу, страницы по 18 записей. При выборе героя виден счётчик заполнения каждого ранга. «В каталоге» означает доступность дизайна для просмотра, а не получение предмета пользователем.

## Права и состояния

| Действие | PLAYER / TESTER / MODERATOR | ADMIN / OWNER |
| --- | --- | --- |
| Создать и изменить свой черновик | Да | Да |
| Смотреть чужой неопубликованный черновик | Нет | Только отправленные/проверенные карточки через административный доступ |
| Отправить или отозвать свою заявку | Да | Да |
| Публиковать, вернуть на доработку, снять публикацию | Нет | `cards.publish` и действующее подтверждение TOTP |
| Незаметно изменить опубликованное изображение | Нет | Нет; нужно создать новый дизайн |

Путь: `DRAFT → PENDING → PUBLISHED` либо `REJECTED → DRAFT → PENDING`. Автор может вернуть ожидающую заявку в черновики. Администратор может снять опубликованную карточку: `PUBLISHED → ARCHIVED`. Повторная публикация снятой версии в этот этап не входит; исправление создаётся новым дизайном.

Каждое изменение проверяет `revision`. Если автор отозвал заявку или другой администратор уже решил её судьбу, старое решение получает 409. Пояснение сотрудника видно автору. Действия записываются в существующий AuditLog. ADMIN может публиковать собственный отправленный дизайн; обязательное правило второго сотрудника не вводилось.

Для обычного пользователя: три новых черновика за скользящие 24 часа, максимум десять открытых. Удаление черновика не обнуляет дневной счётчик. Для ADMIN/OWNER: 100 новых за сутки и 500 открытых для подготовки большого каталога. За заявки и публикацию жетоны не выдаются.

## Изображения и сохранение

Браузер принимает статичные PNG/JPEG/WebP до 8 МБ, уменьшает до 960 px по длинной стороне и отправляет JPEG до 300 КБ. Сервер повторно проверяет формат, размер, габариты и число кадров; сохраняет очищенный WebP без EXIF и исходных метаданных. Минимальная сторона — 240 px. Неподходящий файл отклоняется с объяснением.

Сервер не скачивает изображение по пользовательской ссылке. HTTPS-источник — ссылка для проверки авторства. Перед отправкой нужны изображение, подпись автора и подтверждение возможности использования/публикации. Это не автоматическая проверка прав на чужую работу: её проверяет администратор.

Изображения хранятся в PostgreSQL и попадают в существующий SQL backup; отдельный Docker volume сейчас не требуется. В списках бинарное поле загружается отложенно, изображения выдаются отдельным запросом и только при подходящих правах. Максимум 300 КБ на дизайн: 370 дизайнов — до 111 МБ бинарных данных, дополнительно нужны место под черновики, PostgreSQL/WAL и резервные копии. При росте каталога перенос в объектное хранилище можно рассмотреть отдельно.

Удаление аккаунта удаляет его неопубликованные проекты, шифры и жетоны. Опубликованные/архивированные дизайны и указанная публичная подпись сохраняются без ссылки на удалённый аккаунт. Это явно отделено от личного баланса и истории действий.

## Жетоны и шифр бюро

Секрет — четыре различных символа из шести. Ответ показывает количество точных совпадений и символов на другой позиции. После шести неудачных попыток открывается разбор; завершение с помощью приносит ту же награду, с отдельным состоянием `ASSISTED`.

- Один завершённый шифр = 30 жетонов; максимум пять за неделю, то есть 150.
- Неделя начинается в понедельник 00:00 UTC, время показывается локально.
- Партия сохраняется между устройствами. Повтор старого запроса не расходует попытку и не начисляет второй раз.
- Баланс считается по отдельному `archive_ledger`; XP и `reward_ledger` не затрагиваются.
- Сервер проверяет решение, лимит и выдачу. Клиент не передаёт сумму награды или итоговый баланс.
- Одновременное открытие/решение сериализуется блокировкой пользователя; уникальные ограничения страхуют слот и запись начисления.

В этом этапе жетоны **накапливаются**. Паки, инвентарь полученных карточек, обмен дублей и покупка за жетоны ещё не включены. Экран истории прямо это объясняет. Старый вариант баланса с тремя редкостями из vault нельзя автоматически применять к девяти новым рангам. Стартовый конверт и бесконечная тренировка также не заявляются готовыми.

## Изменения сервера

Миграция `0016` добавляет `archive_cards`, `archive_ciphers`, `archive_ledger`; существующие таблицы данных игроков не преобразует. Нужен обычный `scripts/deploy-current.sh` после принятия PR, с существующим предмиграционным backup. На рабочем сервере изменения в рамках подготовки PR не запускались.

Добавлена зависимость [Pillow 12.3.0](https://pypi.org/project/pillow/12.3.0/). Стандартный предел HTTP-тела в development поднят до 1 МиБ для загрузки сжатого изображения; production Compose уже задаёт 1 МиБ. Внешние изображения в CSP не разрешались, используются очищенные файлы своего сервера и data URL для собственного предпросмотра.

## Проверка

Локально: форматирование, TypeScript, 49 DOM/компонентных тестов, сборка Vite, проверка состава релиза. Новые сценарии: клавиатура и закрытие меню, правильный revision черновика, отсутствие публикации у автора, отправка заявки, завершение шифра и отказ административного доступа.

В CI: серверные сценарии реальных сессий, ADMIN+TOTP, чужие изображения, смена состояния, потерянный/повторный запрос, ограничения, обработка изображений, отделение от XP; миграция 0015 ↔ 0016 и соответствие ORM; отдельная конкурентная проверка PostgreSQL. Итог CI указан в PR. Локальные серверные тесты не запускались: установка зависимостей в этой среде остановилась на сетевом доступе.

Измерено после сборки: весь JS 528 723 байта, первоначальный JS 292 318, CSS 271 841. Новые экраны подключаются лениво. Общие бюджеты JS/CSS обновлены до 540/280 КБ под реализованные экраны; предел первоначального JS 310 КБ и ограничения изображений сохранены.

Реальный Steam-вход, просмотр на живом телефоне и визуальная приёмка ещё требуют проверки после доступного preview/выкладки. DOM-тесты не подменяют визуальный осмотр.
