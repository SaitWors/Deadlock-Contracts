# Пилот Contract Relay

## Добровольное подключение и проверка дружбы

1. Игрок включает участие в профиле Deadlock Contracts и сам отправляет заявку [служебному аккаунту Relay в Steam](https://steamcommunity.com/id/deadlock-contracts-relay/).
2. Оператор сверяет SteamID64 игрока в админке и в Steam, вручную принимает заявку и проверяет, что аккаунт появился в списке друзей Relay. Для ручной работы со служебным аккаунтом оператор сначала убеждается, что Ingest завершил Steam-сессию. Перед возобновлением Ingest оператор завершает ручную сессию. Вход выполняется через официальный клиент или сайт Steam, учётные данные остаются у оператора.
3. Оператор подтверждает дружбу в админке. Сайт сохраняет время ручной проверки. Если дружба прекращена или подтверждение было ошибочным, оператор снимает отметку. После этого сайт ждёт нового наблюдения. Запоздавшие отметки Relay, сделанные до сброса, не применяются. Отключение участия игроком или администратором удаляет запись и отметку на сайте. Чтобы прекратить дружбу со служебным аккаунтом, нужно отдельно удалить его из друзей в Steam.

Раздел 4.C соглашения Steam ограничивает автоматизированное взаимодействие с платформой. Документация Valve описывает чтение списка друзей через `GetFriendList`, которое требует Web API-ключ и возвращает 401 для закрытого списка. Публичный метод приёма заявок в этом интерфейсе отсутствует. Для автоматического приёма и любых новых запросов к Game Coordinator нужен разрешённый Valve способ работы. [Соглашение Steam, раздел 4.C](https://store.steampowered.com/subscriber_agreement/#4) · [Документация Steamworks](https://partner.steamgames.com/doc/webapi/ISteamUser#GetFriendList)

Пилот на сайте не обращается к Steam от имени Relay. Оригинальный Ingest использует собственный список друзей Steam, ставит найденные матчи друзей перед глобальной очередью в проходе и соблюдает общие квоты. Подтверждение на сайте само по себе не запускает запросы и не меняет порядок работы Ingest. [Код очереди Ingest](https://github.com/deadlock-api/deadlock-api-ingest/blob/d8d51587253c25e09368010d959e7618e0f7a345/src/gc/mod.rs#L279-L283) · [Код проверки бюджета](https://github.com/deadlock-api/deadlock-api-ingest/blob/d8d51587253c25e09368010d959e7618e0f7a345/src/gc/mod.rs#L375-L403)

## Измерение задержки на реальных матчах

Для запуска измерений используйте [протокол пилота и пустой шаблон наблюдений](contract-relay-pilot-measurement.md).

До начала наблюдений зафиксируйте период, одинаковое окно проверки для каждого матча и критерии отбора. Сравнивайте матчи согласившихся участников, чья дружба была подтверждена до начала матча, с матчами согласившейся группы без дружбы с Relay. Сопоставляйте режим игры, период и настройки поиска. Учитывайте матчи один раз и исключайте из сравнения матчи, общие для обеих групп, поскольку данные о них попадают в один Deadlock API. Проверки через Companion, ручные решения и повторные попытки учитывайте отдельно.

Для каждого матча сопоставьте время в UTC по внешнему Match ID:

- **Конец матча.** Используйте `Match.ended_at` из данных провайдера. Отмечайте отсутствующее или некорректное время как пробел в наблюдении. [Модель матча](../app/models.py)
- **Принятие записи от Ingest.** Если установленная версия ведёт `fetched-salts.jsonl`, извлекайте на машине Relay только `match_id`, `ingested_at` и `source`. Файл содержит соли матча и остаётся на машине Relay. Источник `gc` включает как друзей, так и глобальную очередь. Успешный POST фиксирует приём записи, а время её первой публикации требует отдельного наблюдения. [Формат журнала](https://github.com/deadlock-api/deadlock-api-ingest/blob/d8d51587253c25e09368010d959e7618e0f7a345/src/ingestion_cache.rs#L21-L46) · [Запись после успешного POST](https://github.com/deadlock-api/deadlock-api-ingest/blob/d8d51587253c25e09368010d959e7618e0f7a345/src/utils.rs#L130-L135)
- **Обнаружение сайтом и итог проверки.** Используйте `BoardMatchCandidate.captured_at` для `capture_source=PROVIDER_HISTORY` и `BoardOption.settled_at` для итоговой проверки по тому же матчу. Если уже есть наблюдения провайдера по этому Match ID, запишите время последнего ответа без матча и первого ответа с матчем. Сохраняйте текущий интервал опроса и фиксируйте границы наблюдения. [Модели кандидата и контракта](../app/models.py) · [Поиск по истории](../app/worker.py) · [Запись результата](../app/services/evaluator.py)

Отдельно посчитайте задержку от конца матча до обнаружения и до итоговой проверки. Для каждой группы укажите размер выборки, медиану, 90-й перцентиль при достаточной выборке и долю матчей без результата к концу окна. Отмечайте исчерпание квоты, недоступность сервиса и ограничения провайдера. Разница между группами показывает наблюдаемую задержку. Для вывода об эффекте Relay нужны данные о происхождении и доступности конкретных матчей.

По присланному журналу известны прежнее исчерпание 24-часовой квоты и ответ Docker на запрос запуска контейнера. Записей, связывающих конец матча, успешную отправку Relay и завершение проверки, пока нет. Ускорение не измерено.

## Timeweb

После отдельного разрешения на выкладку возьмите проверенный коммит сайта и выполните штатное обновление. Команда использует существующий production Compose, создаёт резервную копию и применяет Alembic. Актуальный head для этой интеграции — `0031`. Steam и Ingest остаются на MCG.

```bash
# Из действующего каталога сайта на Timeweb
docker compose --env-file .env.production -f compose.prod.yaml config --quiet
./scripts/deploy-current.sh
docker compose --env-file .env.production -f compose.prod.yaml exec -T web python -m alembic current --check-heads
```

По умолчанию API обмена выключено. Для запуска пилота оператор устанавливает `CONTRACT_RELAY_ENABLED=true` в существующем `.env.production` и применяет конфигурацию штатным обновлением. Пользовательская часть сайта и ручные отметки доступны при выключенном обмене.

Служебный токен генерируется на MCG из 32 случайных байтов. На Timeweb переносится только SHA-256 всего токена, включая префикс узла и без перевода строки. Передайте дайджест через stdin из закрытого временного файла и удалите файл после загрузки.

```bash
docker compose --env-file .env.production -f compose.prod.yaml exec -T web \
  python -m app.relay_credentials mcg --friendship-writes < /path/to/relay-token.sha256
```

В **Управление → Contract Relay** владелец проходит TOTP и включает узел. Узел без `--friendship-writes` может только отправлять heartbeat. Отключение останавливает запросы узла, отзыв очищает дайджест. Для ротации повторите установку дайджеста с новым токеном на MCG. После отзыва узел включается вручную. Для отката обмена отключите узел или флаг. Новые таблицы можно оставить при откате приложения, чтобы сохранить историю.

## Обмен с MCG

Менеджер на MCG открывает исходящий HTTPS к Timeweb и проверяет сертификат. У него нет доступа к PostgreSQL, браузерной админской сессии и Docker Socket. Локальный сборщик передаёт ему только сводку состояния. Следуйте инструкции менеджера на MCG при отдельном развёртывании.

Все маршруты обмена используют префикс `/api/internal/relay/v1` и служебный Bearer. Префикс токена и его дайджест определяют узел. Служебные запросы ограничены 32 КиБ, 120 запросами в минуту на источник и 60 запросами в минуту на авторизованный узел.

| Метод | Данные |
| --- | --- |
| `GET /participants` | Только SteamID64 и текущий идентификатор согласия активного игрока. Пагинация `after` и `next_cursor`. |
| `POST /heartbeat` | Версия агента, время наблюдения, состояние Ingest, диагностические коды и доступные метрики. Последние 100 принятых записей на узел хранятся в БД. |
| `POST /friendship-status` | До 100 ручных наблюдений с идентификатором согласия. Сервер применяет только новые наблюдения для действующего согласия. |

Ответы и входящие данные не содержат Steam-токенов, VDF, журналов и солей. Сервисные изменения принимают целое `protocol_version: 1` и ISO-время с часовым поясом. Пакет наблюдений принимается в пределах 24 часов и допускает до двух минут расхождения часов вперёд. Повторное или более старое время не изменяет уже сохранённое состояние. По отозванному идентификатору согласия изменения игнорируются, в том числе после нового подключения. Отсутствие подтверждения оставляет состояние неизвестным либо ожидающим, а недоступность Steam обозначается отдельно. После пяти минут без связи узел помечается устаревшим. Свежесть наблюдений Ingest оценивается отдельно.

Доступ к служебным маршрутам ограничен обменом Relay. Роли сайта, ручная админка, проверка контрактов и начисления используют существующий доступ и маршруты. [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html) · [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

## Показатели в админке

Раздел показывает новые попытки, для которых сайт привязал подтверждённый провайдером матч. Он измеряет первое **наблюдение метаданных сайтом**, итог автоматической проверки и задержку между ними. Видны размер выборки, медиана, P90, доля подтверждённых, число неразрешённых и число пропусков метаданных. Интервал отчёта по умолчанию составляет семь дней.

Группы разбиты по режиму, известному состоянию Relay и наблюдаемому сигналу Companion для конкретного матча. Группа без согласия характеризует момент привязки матча, а отсутствие события Companion означает отсутствие сигнала в данных. Квота в момент конкретного матча пока неизвестна. Матчи, которые сайт так и не смог привязать, находятся за пределами этой выборки. История до установки миграции остаётся без первого наблюдения. Для вывода о фактическом эффекте Relay нужен пилот с сопоставимыми группами, учётом общих матчей, доступности провайдера и заранее фиксированным сроком наблюдения.
